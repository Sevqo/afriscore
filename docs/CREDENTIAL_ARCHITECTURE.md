# Credential architecture and selected profile
Owner: AfriCore engineering/security. Reviewed 2026-10-26.

Selected profile: VC Data Model 2.0 secured with JOSE compact JWS, media type application/vc+jwt, ES256 (P-256 ECDSA/SHA-256), protected alg/kid/typ and cty:vc. jose handles signing/verification; private JWKs and credential tokens are sealed using the existing authenticated encryption helper. Node crypto independently verifies exports in scripts/verify-credential.mjs. This is not a Data Integrity proof suite, SD-JWT, DID wallet or certification claim.

Payloads include VC2 context plus inline AfriCore vocabulary, credential ID, typed versioned schema URL, issuer URI, subject URI, minimal claim summary, validity, assurance/method/limitations and two BitstringStatusListEntry references. Exact signed compact-JWS bytes are the canonical commitment input; unsigned JSON reserialization is never used for signature or commitment checks. Minimal profile validation is Zod-backed and rejects unsupported structures, dates, status purposes, algorithms and embedded remote-key URLs. No remote JSON-LD/issuer URL is fetched from untrusted credentials.

An ordinary account can apply as a sandbox issuer but cannot approve itself through workspace permissions. A verified allowlisted trust operator reviews the application. approved_sandbox is explicitly unrecognized for institutional/government authority. Approved types constrain issuance. The holder authorizes specific evidence/type/validity, with expiry and cancellation. Issuer reviews that request, refresh-checks source hashes and signs atomically. Repeat issuance returns the original credential; no signed claim is edited in place.

Status uses separate revocation/suspension signed Bitstring Status List credentials with 131072 bits, GZIP and multibase base64url (u prefix). Index zero is the left-most/high bit of byte zero. Entries are never recycled. Capacity is bounded; operator migration is required before exhaustion. Signed lists expire after five minutes. The API checks its authoritative status store; independent verification checks signed snapshots. Offline verification cannot know changes after its snapshots were issued. Fetch fresh metadata/lists before relying on them.

Presentations use application/vp+jwt, managed-holder signature, recipient audience, nonce, expiry and whole minimal credential envelopes. Grant authorization and one-time retrieval are checked server-side. This is an AfriCore managed presentation profile, not complete OpenID4VP. OpenID4VCI/VP were researched but authorization-server/wallet protocols and external conformance are not implemented. Their feature gates remain closed. Do not advertise OpenID interoperability from internal integration tests.

Primary standards reviewed: https://www.w3.org/TR/vc-data-model/ ; https://www.w3.org/TR/vc-jose-cose/ ; https://www.w3.org/TR/did-core/ ; https://www.w3.org/TR/vc-bitstring-status-list/ ; https://openid.net/specs/openid-4-verifiable-credential-issuance-1_0.html ; https://openid.net/specs/openid-4-verifiable-presentations-1_0-final.html . EIP-712 is not used for credential signing: JOSE is the coherent selected profile, and Ethereum transactions use the normal EVM signer stack.
