# Neon signup verification and returning sign-in

The approved development branch was inspected in Neon Console on 28 October 2026. Existing configuration: email signup enabled, **Verify at Sign-up enabled**, **Verification code selected**, email sign-in enabled, shared provider `auth@mail.myneon.app`, Cloudflare origin trusted, localhost allowed for development, custom auth webhooks disabled. No user was deleted, password reset, verification flag manually promoted or provider configuration weakened for this release.

The browser uses supported `emailOtp.verifyEmail({email,otp})` and `emailOtp.sendVerificationOtp({email,type:'email-verification'})`. Verification input has a numeric keyboard and one-time-code autocomplete; legacy local token links remain a separate development path. Resend validates the address and applies a 60-second client cooldown; the managed provider remains authoritative for expiry, attempts, abuse limits and delivery. Provider/network errors remain visible rather than pretending that a code was accepted.

The repeated prompt's UI root cause was `mode === 'signin' && result.managed`: every managed successful sign-in offered verification while a full-page workspace redirect was loading. It now depends on explicit unverified state. Verified sessions continue normally; new unverified signup and `EMAIL_NOT_VERIFIED` show the verification action. Verification does not run as a login second factor. A legitimate email change still synchronizes the provider's current verified state and preserves stable subject links; it never merges identities by email or bypasses existing conflict checks.

Identity restoration takes the SDK session JWT, force-fetching an expired/opaque cached session when necessary. Server verification retains issuer/audience/EdDSA/expiry, fresh provider ban and email state, token revocation, account revocation time and current workspace membership. Eight-character password minimum remains the owner's explicit choice.

**Acceptance limit:** the owner had no unused controlled mailbox and declined that test step. Actual signup-code receipt, incorrect/expired provider codes and a real mailbox email-change round trip remain unverified; no disposable third-party mailbox was used. The existing synthetic managed QA identity is unverified, so its successful session restoration is not evidence of a verified user's mailbox flow. Local verified-user sign-in/session and identity-change tests remain valid distinct evidence. Do not claim end-to-end email delivery acceptance until a controlled inbox is available.

Primary references: [Neon managed email customization](https://github.com/neondatabase/website/blob/main/content/docs/auth/guides/customize-emails.md), [supported Neon SDK OTP methods](https://github.com/neondatabase/neon-js/blob/main/packages/auth/NEXT-JS.md). No custom email receiver was registered, which would otherwise suppress default managed delivery.
