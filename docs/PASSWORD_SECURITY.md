# Password security

Reviewed 2026-10-27. Existing identities, password hashes and session links were not reset, duplicated or migrated by email. The development identity inventory found one existing non-fixture, verified managed identity. Its password was not read or tested; the owner must sign in through the configured development endpoint using the existing password. Provider and branch selection remain fixed by the private environment and subject-bound identity links.

Sign-in accepts existing non-empty passwords without applying a new-password minimum. A regression creates an existing eight-character password hash and proves sign-in succeeds while registration with that password is rejected. This removes the old twelve-character HTML/login validation failure without weakening new-password creation.

Local account creation and reset enforce 15–200 Unicode code points on the server, allow spaces and long passphrases without composition rules, and reject a small local common/contextual/repeated-password blocklist. This is a bounded initial blocklist, not an exhaustive breach corpus or a compliance claim. Passwords are not sent to an external breach-check service. Existing scrypt hashing, random salts, constant-time comparison, one-use recovery and session revocation remain intact. Existing hashes are not normalized or rehashed differently in this change.

Managed Neon Auth remains responsible for its own server policy and password lifecycle. The AfriCore managed signup/reset UI requests at least 15 characters, but this frontend rule cannot prevent direct calls to a public provider endpoint. A configurable provider-side 15-character/blocklist policy has not been verified or activated. Do not describe that managed policy as enforced by AfriCore's local validator or claim NIST conformance. Qualify the provider's supported server policy before production; no unsupported proxy, provider-table hash rewrite or credential interception was added.

All three password forms share PasswordInput: hidden by default, labelled show/hide control with SVG icons and pressed state, stable input identity, current/new-password autocomplete, paste/password-manager support, and no password value in component storage or logs. The primary action is Sign in/Create account/Send recovery email as appropriate. Forgot password is next to the password field; verification appears in the verification/signup/error state rather than an unrelated login link. Demo access is separate at /demo.

Managed session initialization is single-flight and retries a failed initialization. The directly declared @neondatabase/auth 0.7.0-beta package is the same auth implementation previously reached through the facade's nested dependency; it is not represented as a stable release. Types are inferred from its exported factory. No any or ts-ignore masks were added to the SDK integration. Both workspace typechecks and production builds verify resolution. Open AfriCore.code-workspace if VS Code uses a different project/compiler.

References: [NIST password guidance](https://pages.nist.gov/800-63-4/sp800-63b.html), [Neon SDK source](https://github.com/neondatabase/neon-js/tree/main/packages/auth), [Neon authentication](https://neon.com/docs/auth/overview). References inform the review; production assurance and real mailbox/device acceptance remain separate.
